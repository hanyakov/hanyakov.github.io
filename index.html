01ReliabilityNov 2025 – Sep 2026

Moving stateful clusters between zones

On my CVLed migrations of stateful Kubernetes clusters and services across GCP zones and regions: snapshot and disk-clone migration, regional disks replicated across two zones, zone-balanced node pools, and automatic recovery on failure.

ProblemA customer cluster keeps its data on persistent disks, and a GCP disk lives in one zone. Moving a cluster to another zone, region or disk type meant moving those disks without losing data, and a service that lived in a single zone went down with that zone.

What I built

  • Disk migration in the operator service: a direct disk clone when source and target share a zone, and a snapshot or image followed by a new disk when they don't. Generated names stay valid across repeated migrations.
  • Regional disks replicated across two zones, and migration of existing disks to a new storage class.
  • Service zone moves that drain pods by app label, move the disks and start the service in the target zone. A failed step brings the service back up where it was, and every move is audited.
  • A zone control panel in the admin portal, so these moves run without scripts.

ResultClusters and their services move across zones and regions from one admin screen, and a failed move leaves the service running.

02Distributed systemsJul – Sep 2026

Async disk operations that survive lost callbacks

On my CVRe-architected cluster cloning, migration and archiving as async, callback-driven workflows: an idempotent, race-safe webhook tracks every disk, a pre-flight gate holds provisioning, and a reconciler settles stuck archives from disk evidence.

ProblemCloning, migrating and archiving a cluster are long disk operations. The old flow held a request open while the operator worked, so gateway timeouts looked like failures, cluster setup could start before the disks were ready, and a lost report could leave a cluster marked as archiving for days.

What I built

  • The operator accepts disk jobs, runs them in the background and reports each disk to a callback URL instead of holding the request open.
  • The control plane records every attempt as a per-disk status map. The callback handler merges each report under a lock, so duplicate, late or concurrent callbacks are safe to apply.
  • A pre-flight gate holds cluster setup (namespace, configuration, services) until every disk is ready, and backup and disk cloning now run in parallel.
  • A backstop job fails any operation still running after about 60 minutes, and operator reports retry three times.
  • Archive state is tracked per service. A reconciler settles stuck archives only on evidence from the disks, and a restore brings back exactly the services that were archived.

ResultCluster setup no longer runs on half-copied disks, stuck states settle on their own, and a path that could re-create storage on top of live disks is closed.

03CostJul 2025 – May 2026

Cleaning up idle resources automatically

On my CVAutomated cleanup of idle cloud resources, contributing to an estimated 30% cost reduction: queue-driven auto-deletion of trial clusters with 15-day, 3-day and 24-hour warnings, and a scheduled Spark cleanup routine in Go.

ProblemTrial clusters and old Spark files kept costing money after nobody needed them, and cleaning them up was manual work.

What I built

  • Auto-deletion for trial clusters: each cluster gets a deletion date, a scheduled job queues the clusters that are due, and the owner is warned 15 days, 3 days and 24 hours ahead, with one 5-day extension.
  • Admin search and filters by deletion settings, and deletion settings that carry over correctly when a cluster is cloned or migrated.
  • A cleanup routine in the Go Spark driver service with a configurable schedule. It restarts safely when its settings change and calls a cleanup Cloud Function with a signed JWT.

ResultPart of the work behind an estimated 30% reduction in cloud cost, with the manual cleanup work gone.

04ObservabilityFeb 2025 – Oct 2026

Usage alerts customers set for themselves

On my CVDesigned and shipped usage alerting across 4 services (Go, Node.js, React): budget alerts at 50/80/100% by engine, service, Spark workload or AI model, checked every 4 hours instead of daily for 6x faster detection.

ProblemCustomers learned about high consumption late. The first consumption alerts I built in 2025 ran once a day for the whole cluster, so a spike in one workload could go unnoticed for most of a day.

What I built

  • Rules: a user sets one limit on a metric (monthly consumption, contract consumption, AI tokens or storage) and can narrow it to an engine, a service, a Spark workload or an AI model. Alerts fire at 50%, 80% and 100%.
  • Each level is its own policy in the central alerting engine (Go), so levels open and recover independently and each one emails once per period.
  • Checks run every 4 hours instead of once a day, spread across the hour to avoid load spikes. Usage comes from a service-authenticated endpoint that reads month-to-date usage day by day and caches settled days.
  • Events are stored before any email goes out, recoveries are stored without email, and each rule keeps a delivery history. Rules are capped at 20 per cluster, and a rule that fails to sync rolls back cleanly.
  • Pages in the customer portal and the admin portal (React, TypeScript).

ResultThe worst-case time to notice a crossing dropped from 24 hours to 4, with no extra emails.

One control plane, three clouds

On my CVExpanded multi-cloud support (GCP, AWS, Azure): moved provider logic behind a platform abstraction in a 34-file refactor, and added AWS operator features for S3 uploads, EBS resizing, archiving, DataSync cloning and database imports as Kubernetes Jobs.

ProblemChecks for which cloud a cluster ran on were spread through the control plane, so each platform change meant edits in many places. On AWS, the operator also lacked features the GCP side already had.

ResultAWS clusters gained clone, archive, resize and file management, and platform logic now changes in one place.

06SecurityOct 2025 – Apr 2026

Least-privilege access and credential rotation

On my CVSecured cloud access for platform services: moved the operator to IAM Roles for Service Accounts (IRSA), automated EKS Pod Identity grants, enabled S3 ABAC, and built audited credential rotation through Kubernetes Secrets.

ProblemOn AWS, the operator logged in with stored credentials at start-up, granting a cluster access to its storage was a manual step, and changing a cluster's console password needed an engineer.

What I built

  • Moved the operator to IAM Roles for Service Accounts (IRSA): the pod's Kubernetes service account assumes an IAM role, so no long-lived keys sit in the container.
  • Automated EKS Pod Identity grants for cluster workloads.
  • Enabled attribute-based access control (ABAC) on S3 buckets, so a role only reaches resources whose tags match.
  • Self-service password rotation: the control plane validates and audits the change, the operator updates the Kubernetes Secret, and the cluster's managers are emailed.
  • Signed JWTs for service-to-service calls such as the cleanup function.

ResultNo static AWS keys in the operator, access granted per workload, and every credential change on record.

07Data and FinOpsAug – Oct 2026

A month-end forecast that follows recent usage

On my CVReduced month-end consumption forecast error from 2.9% to 2.0% (31% lower, backtested on 10 production clusters) by switching to a 14-day recent average; built scheduled monthly usage reports per service.

ProblemThe consumption view projected each cluster's month-end usage from its average since the contract started. A cluster that changed its usage kept being projected at the old pace.

What I did

  • Backtested projection methods on 10 production clusters in Python. The average of the last 14 complete days missed month end by 2.0% on average, against 2.9% for the since-contract average.
  • Built it into the burn service: runway, depletion date and the daily threshold alert use the recent average, clusters without a contract get a projection too, and the next two months get a likely range that is wider for Spark-heavy clusters.
  • Scheduled monthly consumption reports per cluster, with a per-service chart and totals against each engine's limit.

ResultMonth-end forecast error 31% lower in the backtest, and a forecast for clusters that had none.
